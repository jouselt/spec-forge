# 12: spec-forge: Proposal

## Problem

Specs get skipped for two opposite reasons. The first is the blank page: the idea is clear in your head, but nobody has written down the questions that turn an idea into a scope, a set of constraints, and a list of testable acceptance criteria. The second is worse, and it is the reason this project exists.

A generated spec can be fluent and wrong. Joe's own `01` and `02` `proposal.md` files were regenerated by a tool and reverted to an older Next.js and OpenAI version, losing text he had written himself. The output read well. It was not what he had decided. A tool that produces plausible content the user never wrote is worse than no tool, because the failure is invisible until someone notices the stack changed.

So this project inverts the usual priority. **Interview first, generate second.** Every generated fact must trace to an answer a human gave. Anything the model adds on its own is marked as inferred, shown differently, and must be reviewed before it can be exported.

## Goal

Build **spec-forge**: a 100% client-side Angular 20.3 app that interviews the user about an idea and produces three markdown files, `proposal.md`, `design.md`, and `tasks.md`, in the shape of the specs in Joe's `portfolio-projects` repository.

Two things come out of it:

1. **The artifact.** Three files the user can download individually or as one bundle, editable in the browser before download.
2. **The argument.** The tool demonstrates spec driven development by being built from a proposal, design, and tasks spec, by generating that same artifact, and by encoding the discipline as software: it will not generate until the hard questions are answered, and it refuses to invent.

No backend. No API key. No GitHub integration, no token, no repo write. Static files on GitHub Pages, the same deployment model as project 11.

## Target Signal

The signal is the artifact: a finished spec whose every sentence traces to an answer, produced by a run that cannot skip the hard questions.

A visitor opens the page on a laptop with no account and no model loaded. They answer nine steps about an idea they actually have. Step four asks "what proves this worked" and refuses to accept "it works" as an answer. They reach the generate step, see three tabs of markdown, and see a panel that says: 41 of 44 blocks came from your answers, 3 were added by the model and need your review. They confirm two, delete one, download the bundle.

The interesting problem is not generating markdown, it is making sure the markdown cannot invent. Provenance is stored per block, the gate blocks export on unreviewed inferred text, and the diff before apply stops a regeneration from reverting work. That is what the tool has to prove about itself.

Measured at the end of a run: three files where every block carries an origin, zero inferred blocks with no model loaded, and export enabled without a review step.

## Constraints Measured Up Front

Measured values are marked. Budgets are marked as budgets, and the app computes them at runtime from the selected model rather than hardcoding them.

**Browser model limits (measured from the WebLLM `prebuiltAppConfig`, same source as project 11):**

| Model | VRAM | Context (tokens) |
| --- | --- | --- |
| Llama-3.2-1B-Instruct-q4f16_1 | 879 MB | 4096 |
| gemma-2-2b-it-q4f16_1 | 1895 MB | 4096 |
| Qwen2.5-3B-Instruct-q4f16_1 | 2504 MB | 4096 |
| Qwen3-4B-q4f16_1 | 3431 MB | 4096 |
| Qwen2.5-7B-Instruct-q4f16_1 | 5106 MB | 4096 |

`context_window_size` is 4096 for nearly every usable model; some models ship a `-1k` variant at 1024. This is the number that decides whether the model shaping path runs at all.

**Interview payload (budget, not measured):** a completed interview is estimated at 20 to 32 answered questions, roughly 900 to 1,600 words, about 1,200 to 2,100 tokens by the `chars/4` heuristic. Per-file shaping only sends the answers mapped to that file, estimated at 400 to 700 tokens. With a 256-token template reserve and a per-file output reserve of 900 to 1,400 tokens, a single pass fits 4096. It does not fit 1024. On a `-1k` model the app drops the model path for that file, says so, and falls back to template assembly. The check is computed at runtime.

**Local model availability (measured constraint, and the reason for the design):** Joe's Ollama runs on his homelab at `http://localhost:11434`. A static site served from GitHub Pages cannot reach a visitor's localhost, and asking a visitor to run Ollama is not a demo. Browser inference through WebGPU is the only local option available to a static page. That is why WebLLM is optional and why the no-model template path is the default.

## Tech Stack

- **Framework**: Angular 20.3, standalone components, signals, TypeScript strict with `strictTemplates`. No state library, no Reactive Forms in the wizard (the question graph is dynamic; see the trade-offs in `design.md`).
- **Inference (optional)**: `@mlc-ai/web-llm` in a dedicated Web Worker, WebGPU primary with a WASM fallback. LiteRT.js (`@litertjs/core`) behind the same `ModelProvider` seam as project 11, as an alternate backend.
- **Markdown editing**: CodeMirror 6 with `@codemirror/lang-markdown`, one editor instance per tab.
- **Persistence**: IndexedDB via `idb`. Answers autosave, so a long interview survives a reload.
- **Deterministic core**: question graph, trigger detection, answer-to-section mapping, template rendering, diff, validation, and the export gate are pure functions with no model in the loop. These are the parts that carry the project.
- **Export**: `Blob` plus object URLs for individual files; a concatenated `.md` bundle by default, optional `.zip` through `fflate` loaded by dynamic import.
- **Deployment**: static build to GitHub Pages at `jouselt.github.io/spec-forge`, no server.

## Core Features

1. **Guided interview.** Nine base steps: the idea, the problem and who has it, the current workaround, goal and non-goals, the target signal and the proof metric, constraints measured up front, stack, scope boundary, risks and trade-offs, acceptance criteria and timeline.
2. **Adaptive follow-ups.** Later questions are driven by earlier answers. Mentioning a local model asks about context window, VRAM, and WASM fallback tolerance. Mentioning a corpus asks about document count, word count, and vector dimensions. Every adaptive question shows what triggered it: "Asked because you mentioned a local model in step 1."
3. **Two generation paths.** Template assembly from answers alone is the default and needs no model; every block traces to an answer. Optional model shaping runs in a worker and only rewrites prose and proposes acceptance criteria. Both paths emit the same provenance structure.
4. **Per-block provenance.** Every generated block records its origin: the answer ids it came from, a template frame, the model that inferred it, or a user edit. The panel shows the counts and lets you jump from a block back to the answer that produced it.
5. **Unsourced content gate.** Export is blocked by default while any block is model-inferred and unreviewed. The user confirms, edits, or rejects each one. A no-model run has zero inferred blocks and exports immediately, which is the point.
6. **The model asks, it does not answer.** When the shaping model lacks a fact, it emits a placeholder naming the question it would ask. Those placeholders become chips the user can promote into real interview questions. The model proposes questions, never facts.
7. **Regression guard.** Every generation is versioned. Re-generation shows a line diff before applying, locked sections are never overwritten, and any previous version can be restored from a snapshot. This is the direct answer to the failure that started the project.
8. **Import an existing spec.** Paste a `proposal.md` you already have. The app parses `##` sections and merges into them instead of replacing them, so regenerating cannot revert your text.
9. **Autosave and resume.** Answers, generated sections, review states, and snapshots persist to IndexedDB. Closing the tab mid-interview loses nothing.
10. **Style lint.** A deterministic check for em dashes and a checked-in banned-word list, applied to generated output. The same list this repo enforces on its own specs.

## Output Shape

The generated files match the section structure measured across the eleven existing specs in `portfolio-projects`, which is the corpus this was derived from:

- **`proposal.md`**: Problem, Goal, Target Signal, Constraints Measured Up Front, Tech Stack, Core Features, Scope Boundary, Why This Differentiates..., Timeline, Acceptance Criteria, Risks.
- **`design.md`**: Architecture (ASCII diagram), Package layout, Data model or the equivalent core model, Provider seams, Validation and Provenance, Worker Protocol, Persistence, Trade-offs Considered, What This Proves, Acceptance Criteria (design-verifiable), Open Questions.
- **`tasks.md`**: Phase 1..N, each item a checkbox tagged `[G]` gate test, `[E]` eval, or `[M]` manual verification, ending with a Definition of Done.

The six sections shared by every existing spec are required: Problem, Goal, Target Signal, Tech Stack, Acceptance Criteria, Trade-offs. The validator refuses to emit a file missing one.

## Scope Boundary

This project is separate and independent from project 11 (`md-skill-forge`). No integration, no shared package, no pipeline where one feeds the other. They share architectural patterns, both being client-side Angular apps with optional WebLLM inference behind a `ModelProvider` seam, and that is the only relationship.

**In scope**: the interview, adaptive questions, autosave, both generation paths, provenance, the unsourced gate, editable output, diff before apply, snapshots, import and merge, export, static deploy.

**Out of scope**: any repo or GitHub API integration, accounts, cloud inference, collaborative editing, PDF or DOCX export, and generating code from a spec. This tool produces the three markdown files and stops there.

## Why This Differentiates a Senior Angular Engineer

- **The hard part is the constraint, not the prompt.** A tool that cannot invent is a harder engineering problem than one that always produces text. The gate, the provenance model, and the placeholder protocol are the product.
- **Honest limits are shipped as features.** The export gate, the refusal to run the model path on a small context window, and the style lint all tell the user what the tool cannot do. A tool that admits what it cannot know reads as senior.
- **Deterministic core, model at the edge.** Trigger detection, mapping, templates, diff, and validation are pure tested functions. The model is an optional last-mile prose shaper with a budget check in front of it.
- **The regression guard is built from a real failure.** Snapshots, locks, and diff-before-apply exist because a regeneration destroyed real work. Shipping the guard proves the lesson was learned, not just noted.
- **Angular 20.3 with signals and no state library.** A dynamic question graph, a draft, and three generated documents do not need NgRx. Knowing what not to add is the senior call.
- **The project demonstrates its own thesis.** Built from a spec, generates that spec, and encodes the discipline as software. It is spec driven development all the way down, which is a rare thing to be able to show rather than claim.

## Acceptance Criteria

- [ ] Completing the nine base steps with no model loaded produces three files that pass `spec-validator.ts`, with zero inferred blocks and export enabled immediately.
- [ ] Mentioning "a local model with Ollama" in step 1 adds the context window, VRAM, and WASM fallback questions, each labelled with the answer and the matched phrase that triggered it.
- [ ] Export is blocked while at least one block is inferred and unreviewed, and the blocking dialog names the section and the number of blocks.
- [ ] Confirming or editing every inferred block unblocks export; rejecting one removes its text and unblocks export.
- [ ] Shaping a file when `inputTokens + templateReserve + outputReserve > contextTokens` refuses the model path for that file, states the numbers, and falls back to template assembly.
- [ ] A `{{MISSING: ...}}` placeholder emitted by the model appears as a chip in the review panel, and promoting it adds a question to the interview.
- [ ] Re-running generation with a locked section shows a diff for the unlocked sections only and leaves the locked text byte-identical.
- [ ] Killing the tab at step 7 and reopening restores all answers, generated sections, and review states.
- [ ] Importing Joe's real `01` `proposal.md` and regenerating produces a file that still contains the original Problem and Goal text verbatim.
- [ ] A run with the model path disabled has zero inferred blocks; the export report states the counts per origin kind and they sum to the total block count.
- [ ] Style lint flags an em dash and each word on the banned list in a fixture, and passes on the three specs committed in this repo.
- [ ] The self-regeneration test rebuilds this project's three files from `spec-forge-answers.json` through the template path and asserts every required heading is present and the acceptance criteria counts match.
- [ ] Static deploy on GitHub Pages; DevTools Network shows zero requests after model weights are cached.
- [ ] Keypress-to-render latency in the answer inputs stays under 50 ms while a shaping run streams, measured with `performance.now()`.

## Risks

| Risk | Mitigation |
| --- | --- |
| The model invents facts that read as true | Marker protocol makes unmarked text inferred by construction; inferred blocks are visually distinct and gated at export |
| Adaptive questions run away and the interview gets long | Hard cap of 12 adaptive questions and 3 per trigger, with a visible counter |
| Template output reads mechanical | Templates carry several frames per section, chosen by answer shape; the model path exists for users who want prose, and is optional |
| Small models ignore the marker protocol | Deterministic validator counts markers per section; under 60% coverage the run is marked failed and the template output is kept |
| A generation reverts user work | Snapshots, per-section locks, diff before apply, and import-merge. Four independent guards on one failure mode |
| Bundle size grows with CodeMirror and fflate | CodeMirror is ~200 KB and tree-shaken; fflate is behind a dynamic import and never in the main chunk |
| The demo looks like a form | The provenance panel, export report, and self-regeneration test are the demo. The README leads with them |
